# Installation — zero to a working network

Set up a Distributed Dimensions network from nothing: one Velocity proxy, three Paper
backends (Overworld / Nether / End), a shared database, and HuskSync for player data.
Everything here is host-native — no containers, no mocks, no partial infra.

At the end you will have:

```
overworld backend (port 25566) ─┐
nether   backend (port 25567) ──┼─► Velocity proxy (port 25565) ◄── players
end      backend (port 25568) ──┘        + shared DB (port 3306)
```

> Prerequisite honesty, from the start: this build is **pre-release** and has never been
> run as a full live network (see `docs/limitations.md`). Install it on a staging network
> first. If you cannot accept that, wait for a release.

## 1. What you need

| Component | Requirement |
|---|---|
| Java | **25** on the proxy and on every backend (Velocity 4.2+ and the Paper 26.3-family both require it) |
| Backends | **Paper 26.3+ or Folia 26.3+**, one per dimension. `folia-supported: true` in the plugin metadata |
| Proxy | **Velocity 4.2+** |
| Database | **Required.** MySQL 8+ / MariaDB / PostgreSQL, **or** MongoDB. The transfer journal lives here; without it the backends boot fail-closed and refuse every transfer |
| Redis | **Not used by this plugin.** `redis.enabled` is reserved and read by nothing. HuskSync (below) requires its own Redis 5+; that is HuskSync's requirement, not ours |
| External sync plugin | **Required for correctness.** HuskSync is the tested/recommended path. Without any sync plugin, player data (inventory, XP, effects…) is never moved between backends by us — install one or accept silent staleness |
| OS/network | Hosts that can reach each other on the backend ports, one publicly reachable port (the proxy's) |

Other sync plugins (MC Data Bridge, InvSYNC, …) work in degraded/assumed mode only —
see `docs/player-sync.md`. "Any modern sync plugin" is aspirational; HuskSync is the
answer with evidence behind it.

## 2. Build or obtain the jars

Building from source (Java 25; Gradle downloads the toolchain if missing):

```bash
git clone <repo-url> Distributed-Dimensions
cd Distributed-Dimensions
./gradlew build
```

Artifacts:

```
paper/build/libs/distributed-dimensions-paper-1.0.0.jar      → the backends
velocity/build/libs/distributed-dimensions-velocity-1.0.0.jar → the proxy
```

The jars embed all libraries (Configurate, JDBC drivers, Mongo driver, HikariCP) — nothing
else to download. The public API (`distributed-dimensions-api`) is already shaded into the
backend jar; third-party plugins should use `compileOnly` coordinates from `docs/api.md`.

## 3. Network plan (example)

| Host role | Bind address | Port | Public? |
|---|---|---|---|
| Velocity proxy | `0.0.0.0` | 25565 | **yes** |
| Overworld backend | `127.0.0.1` (or private VLAN) | 25566 | no |
| Nether backend | `127.0.0.1` (or private VLAN) | 25567 | no |
| End backend | `127.0.0.1` (or private VLAN) | 25568 | no |
| MySQL/MariaDB | `127.0.0.1` | 3306 | no |
| Redis (HuskSync only) | `127.0.0.1` | 6379 | no |

Firewall rule of thumb: **only 25565 is open to the internet.** Backends reachable only
from the proxy host/VLAN; the database reachable only from the three backends (and from
HuskSync). The runtime trust model assumes backends are on a private network — a publicly
exposed backend with `online-mode=false` is an open door.

## 4. Prepare the shared database

The plugin needs one database for its own state (transfer journal, respawn points — **not**
player data; that's HuskSync's). All three backends **must point at the same store**.

MySQL / MariaDB (recommended):

```sql
CREATE DATABASE distributed_dimensions CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
-- restrict the host to the backends' address where possible; '%' only inside a private VLAN
CREATE USER 'distributed_dimensions'@'%' IDENTIFIED BY 'pick-a-long-random-password';
GRANT ALL PRIVILEGES ON distributed_dimensions.* TO 'distributed_dimensions'@'%';
FLUSH PRIVILEGES;
```

PostgreSQL:

```sql
CREATE DATABASE distributed_dimensions;
CREATE USER distributed_dimensions WITH PASSWORD 'pick-a-long-random-password';
GRANT ALL PRIVILEGES ON DATABASE distributed_dimensions TO distributed_dimensions;
```

MongoDB (alternative, same requirement — all three backends, one store):

```
mongodb://localhost:27017  →  database: distributed_dimensions
```

Tables/collections are created and migrated automatically on first boot
(`<prefix>transfer_operations`, `<prefix>respawn_points`, `<prefix>portal_index`; default
prefix `dd_`). No manual DDL. A backend that cannot migrate boots **fail-closed** and
refuses all transfers until fixed — check its log first, always.

## 5. Configure the proxy

Folder layout after first boot:

```
velocity/
├─ velocity.toml
├─ forwarding.secret          ← generated by the proxy on first boot; guard it
└─ plugins/
   └─ distributed-dimensions-velocity-1.0.0.jar
```

Minimal `velocity.toml` for this network (only the relevant parts):

```toml
bind = "0.0.0.0:25565"
motd = "A dimension network"
show-max-players = 100

# The proxy authenticates with Mojang; backends do NOT (see §6 backends step).
online-mode = true
# default-on since 3.x; listed for completeness, not required for this to work
force-key-authentication = true

# modern forwarding: identity + IP forwarding with a MAC. REQUIRED.
player-info-forwarding-mode = "modern"
# forwarding-secret-file defaults to "forwarding.secret"; the proxy creates the file
# with a random secret on first boot. Do not edit it; do not commit it.

[servers]
  overworld = "127.0.0.1:25566"
  nether    = "127.0.0.1:25567"
  end       = "127.0.0.1:25568"
  try = ["overworld"]

[forced-hosts]
# leave empty unless you route domains per-backend
```

Notes that bite people:

- **The server names in `velocity.toml` (`overworld`/`nether`/`end`) are the names the
  plugin routes by.** `network.dimensions.*.server` in every backend's `config.yml` must
  match them exactly, case-sensitively.
- **`online-mode = true`** on the proxy, and `online-mode = false` on the backends. The
  proxy is the authentication authority; backends must not try to re-authenticate.
- `forwarding.secret` is read by every backend (next step) — they all need the **same**
  secret, and the secret stays on the proxy + backends only.
- `bungee-plugin-message-channel` can stay at its default; we do not use it.
- **Do not restart the proxy during transfer waves** — proxy restarts erase the in-memory
  idempotency cache; in-flight replays then re-execute (Velocity's own statuses make this
  usually harmless, but it is not free).

### Proxy-side plugin config

On first boot the proxy writes `plugins/distributeddimensions/config.yml` (same bundled
schema as the backends). The only keys the proxy reads:

```yaml
network:
  transfer:
    timeout: 10000        # ms budget for the whole connect operation; also arms 2x watchdogs
  dimensions:
    overworld:
      server: "overworld"                # = the velocity.toml name, exactly
      dimension: "minecraft:overworld"
    nether:
      server: "nether"
      dimension: "minecraft:the_nether"
    end:
      server: "end"
      dimension: "minecraft:the_end"
config-version: 2
```

The proxy **ignores** `database.*` (it holds no durable state) and does not need `sync.*`.
Dimension values are matched literally. A broken proxy config does not crash the proxy — it
enables **fail-closed**: every transfer request is refused with `UNAVAILABLE` naming the
problem, and `/ddproxy reload` re-enables routing after a clean load (last-good is kept on a
failed reload).

Health check after first boot:

```
/ddproxy status
```

Expect: `config: healthy`, `channel: distributeddimensions:transfer (registered)`, the
`dimensions:` routing table, `0 in flight`, and the counters block. If `config: BROKEN` —
fix `plugins/distributeddimensions/config.yml`, then `/ddproxy reload`.

## 6. Configure each backend (do this ×3)

Each backend is a normal Paper/Folia server of its dimension. The three share the jar and
differ in `server.properties` + `paper-global.yml` + backend `config.yml`.

### 6.1 Vanilla-side hardening (per backend)

`server.properties`:

```properties
online-mode=false
server-port=25566        # 25567 nether, 25568 end
```

`spigot.yml`: make sure `settings.bungeecord=false` (it is by default; leaving it `true`
after moving to Velocity modern forwarding is a classic source of subtle bugs).

`config/paper-global.yml`:

```yaml
proxies:
  velocity:
    enabled: true
    online-mode: true          # MUST match online-mode in velocity.toml
    secret: "paste-the-contents-of-forwarding.secret-here"
```

**About `prevent-proxy-connections`.** It is a vanilla `server.properties` key and it does
something specific: kicks players whose ISP/AS differs from Mojang's authentication server.
It does **not** prevent players from connecting directly to the backend, and it is **not**
the mechanism that protects a backend behind Velocity — the forwarding secret in
`paper-global.yml` is. Leave it at its default (`false`) unless you specifically want
anti-VPN kicks; turning it on behind Velocity buys you nothing for backend protection and
can false-kick legitimate players. The backend is protected by (a) the secret check, and
(b) being unreachable except through the proxy (bind + firewall it — see §3).

### 6.2 The backend plugin's config.yml

Backend config lives at `plugins/DistributedDimensions/config.yml`. The keys that matter
for a fresh network:

```yaml
database:
  type: "mysql"                                # mysql | mariadb | postgresql | mongodb
  jdbc-url: "jdbc:mysql://127.0.0.1:3306/distributed_dimensions"
  username: "distributed_dimensions"
  password: "${DB_PASSWORD}"                    # or a literal password (discouraged)
  table-prefix: "dd_"
  maximum-pool-size: 10
  minimum-idle: 2
  connection-timeout: 5000

network:
  proxy:
    enabled: true
  transfer:
    timeout: 10000                              # keep identical on proxy and backends
  dimensions:
    overworld:
      server: "overworld"                       # = velocity.toml name, EXACT
      dimension: "minecraft:overworld"
    nether:
      server: "nether"
      dimension: "minecraft:the_nether"
    end:
      server: "end"
      dimension: "minecraft:the_end"

sync:
  enabled: true
  plugin: "auto"                                # HuskSync auto-detected; see §7
  wait-timeout: 5000
  wait-ticks: 20

mirage:
  enabled: true                                 # void stub worlds for the other dimensions
```

Critical, and easy to get wrong:

- **The `database.*` block is identical on all three backends** — one store, one journal.
  If one backend points elsewhere, the End exit portal "forgets" every respawn point and
  transfers can dangle non-terminal.
- **`network.dimensions.*.server` = the `velocity.toml` names.** All three backends carry
  the same table (each knows how to reach every dimension).
- `${DB_PASSWORD}` is expanded **at load time** against the process environment; an unset
  variable is a hard failure naming the variable, never its value. Set it in the backend's
  environment (e.g. `Environment=DB_PASSWORD=...` in a systemd unit, or export in the start
  script). Local dev with trust-auth MySQL may use `password: ""`.
- **The proxy does not need this file's `database.*`** — the proxy never opens the journal.
- **Proxy vs backend plugin names differ**: the proxy jar runs from
  `plugins/distributed-dimensions-velocity-1.0.0.jar` with data at `plugins/distributeddimensions/`;
  the backend jar at `plugins/distributed-dimensions-paper-1.0.0.jar` with data at
  `plugins/DistributedDimensions/`.
- **No `network.source-server` key exists in `config.yml`.** Portal/End flows derive the
  backend's own server name from the `network.dimensions` slot that matches the dimension
  being served, so they work out of the box. The system property
  `-Ddimensions.source-server=<name>` (or env var `DD_SOURCE_SERVER=<name>`) is only needed
  for the mirage-guard / programmatic-API path (`ChannelCrossServerTransfer`); set it on
  every backend anyway so mirage teleports (`/tp` into a mirage world) can route:
  `java -Ddimensions.source-server=overworld -jar paper-26.3.jar nogui`
  (`nether` / `end` on the other two) — without it, mirage-routed transfers fail closed
  with `UNAVAILABLE`, loudly. This is deliberate: the proxy cross-checks the claim against
  the connection, so the backend must know its name.
- `config-version: 2` — never edit by hand; migrations run automatically on open.

### 6.3 Mirage worlds

Defaults are correct for default level-name setups: `world` / `world_nether` /
`world_the_end`. On the Overworld backend the mirage `world_nether` and `world_the_end` are
void stubs with the Nether/End environment — **they are supposed to be there and empty**.
Override `mirage.names` only for non-standard level names (see `docs/mirage-dimensions.md`).
`mirage.enabled: false` disables the stubs and guards entirely.

## 7. HuskSync (required for correctness of the arrival point)

Install HuskSync on **all three backends** — never on the proxy. Per backend, in
`plugins/HuskSync/`:

1. **Same HuskSync database** (a different schema/database on your existing MySQL, or its
   own instance — HuskSync supports MySQL 8+, MariaDB, PostgreSQL, MongoDB) and **a Redis
   5.0+ server for HuskSync's own use**. Distributed Dimensions itself does not touch
   Redis; HuskSync requires it (e.g. `redis://127.0.0.1:6379`).
2. **`server.yml` on each backend: the `name:` must equal that backend's `velocity.toml`
   server name** (`overworld` / `nether` / `end`). This is HuskSync's requirement; getting
   it wrong routes snapshots to the wrong server.
3. **Disable location sync. Mandatory.** In each backend's HuskSync `config.yml`:

   ```yaml
   synchronization:
     features:
       location: false
   ```

   (Off by default in HuskSync v4. If enabled, applied snapshots can overwrite our arrival
   coordinates *after* the transfer positions the player — the "player warped back to the
   old server's coordinates" bug. Keep it off even for "same-shaped" worlds; our arrival
   flow positions the player itself. The snapshot type is `husksync:location`.)
4. HuskSync writes its own tables/collections on first boot; the errors it prints before
   you add credentials are expected.
5. Locked-map sync and all other HuskSync features may stay at HuskSync defaults; only
   `location` is destructive to this plugin's arrival positioning.
6. HuskSync is officially Paper/Fabric-only. On Folia it is unofficial — verify on your
   build before relying on it there.
7. Restart all three backends after configuration; watch for HuskSync's "Connected to
   database/Redis" lines.

If HuskSync is absent entirely, the backend logs `sync: level D (degraded-fallback)` and
arrives players with a fixed delay **without any confirmation** that data was applied —
inventory may be stale for a moment, and nothing heals it. Do not run production without a
sync plugin unless you have read that sentence twice.

## 8. Boot order

1. Database up (`mysql`/`psql`/`mongosh "ping"` healthy).
2. **Proxy** first: `java -jar velocity.jar` (creates `forwarding.secret` on first boot).
3. **Backends** in any order: overworld, nether, end.
4. First boot on a backend writes `plugins/DistributedDimensions/config.yml` (edit it, then
   restart) and creates/migrates the journal tables.

Wait for each backend's `Distributed Dimensions enabled cleanly` line before testing.

## 9. Verification checklist

**Proxy (`plugins/…` logs, then console):**

```text
[INFO] Distributed Dimensions enabled (channel distributeddimensions:transfer)
```

`enabled in DEGRADED mode` instead → config broken; fix and `/ddproxy reload`.
Run `/ddproxy status`: `config: healthy`, channel registered, the three `dimensions:`
lines, `0 in flight`.

**Each backend (logs):**

```text
[INFO] configuration: source=FILE file-created=false config-version=2 warnings=0 notes=…
[INFO] dimensions: minecraft:overworld -> server 'overworld'
[INFO] dimensions: minecraft:the_nether -> server 'nether'
[INFO] dimensions: minecraft:the_end -> server 'end'
[INFO] persistence ready (engine=mysql, tablePrefix=dd_, pool=10/2)
[INFO] chunk tickets: enabled, ttl=300 ticks, ring-of-8=true
[INFO] mirage: ready — 2 created, 1 already present (real worlds)
[INFO] sync: level A (husksync-api) bound — strategy=husksync-api, plugin=HuskSync, …
[INFO] Distributed Dimensions enabled cleanly (1234 ms)
```

Any `SEVERE` line instead → the backend is DEGRADED by design; transfers will be refused.
Fix the cause named in the line (usually persistence or config), restart, re-check.

**In-game (creative test network):**

1. `/server overworld`, build an End portal frame, light it.
2. Enter → you should appear on the **End backend** on the obsidian platform (100.5, 49, 0.5).
3. `/ddproxy transfers 3` on the proxy shows a `SUCCESS` row with both server names.
4. Kill the dragon (or `/kill @s`-equivalent test exit) → exit portal returns you to your
   recorded respawn point (bed/anchor), or world spawn if none.
5. Nether portals: **not wired in this build** — do not test them; they will not work.

**Mirage sanity:** every backend lists `world`, `world_nether`, `world_the_end` (or your
level-name equivalents). The foreign two are empty void stubs — expected. `/execute in
minecraft:the_nether run …` behavior with multiple worlds of one dimension type is
version-dependent and not a reliable assertion — ignore it.

## 10. Ports and firewall recap

| Port | Service | Reachability |
|---|---|---|
| 25565 | Velocity proxy | public |
| 25566–25568 | backend Paper/Folia | proxy host + your LAN only; **firewall to 127.0.0.1 or VLAN** |
| 3306 | MySQL/MariaDB | backends (+ HuskSync) only |
| 6379 | Redis (HuskSync only) | backends only |
| 25575 | RCON (if enabled) | localhost only — or don't enable it |

Backends bound to `0.0.0.0` with `online-mode=false` are directly joinable with any UUID —
firewall them or bind `127.0.0.1` and proxy over the loopback/ private interface.

## 11. Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Portals refuse: "You cannot travel there right now" / player stays put; no transfer | Backend DEGRADED — config fallback, persistence failed, or mis-wired `network.dimensions` slot | Read the backend log for the `SEVERE` reason lines; fix file; restart. `isHealthy() == false` never means the process died — it means transfers are refused |
| `SEVERE: persistence failed to start` | DB down / wrong credentials / migration failed | Check DB reachability, `${DB_PASSWORD}` value, `dd_` prefix migrations. Restart after fix |
| Transfers get stuck; player kicked to source after ~20 s | Proxy never answered / watchdog (2 × `network.transfer.timeout`) fired | `/ddproxy transfers 5`; check proxy log for `BACKEND_DOWN`/`TIMEOUT`; check backend ports reachable from proxy host; raise `timeout` if the backend genuinely needs >10 s to accept a login |
| Player arrives but inventory/XP stale or wrong | Sync plugin missing/not applying — degraded mode or HuskSync apply never completes | HuskSync: check its log, DB + Redis connectivity, `server.yml` names. Our side: look for `level D` / `SyncTimeoutException` lines; `sync.wait-timeout: 10000`. Remember: this build does not await sync in the arrival flow (see `docs/limitations.md`) |
| Player re-appears at the previous server's coordinates / old spot after arrival | HuskSync `synchronization.features.location: true` | Set it to `false` on **every** backend; restart; re-test |
| `husksync-api` never binds; `level D (degraded-fallback)` logged | HuskSync not installed / wrong jar / load order | Install HuskSync on all backends (not proxy); it must be Paper/Fabric; check the `level A` line after restart |
| `HuskSync API incompatible` | HuskSync older than the public-events API | Upgrade HuskSync (4.1.0+ for 26.3) |
| End exit portal always sends players to world spawn | No respawn records / backends not sharing the DB / record dimension unroutable | Point all backends at the same DB; bed/anchor interactions must happen on backends where recording is enabled; check backend logs for `respawn store read failed` |
| Mirage worlds listed / placeholder plugins count 3 worlds per backend | Intended | Nothing to fix (or `mirage.enabled: false`) |
| `/execute in minecraft:the_nether run tp @s …` teleports me nowhere useful | Version-dependent vanilla behavior + mirage is void | Ignore; mirage routing happens via normal teleports/`/tp` into the mirage world |
| Proxy: `/ddproxy status` shows `config: BROKEN` | Proxy `config.yml` broken | Fix file; `/ddproxy reload` — last-good is kept meanwhile |
| Transfer works but `DimensionTransferCompleteEvent` listener never sees post-sync state | Expected on this build | The arrival flow does not await the sync plugin yet; wait for the sync plugin's own signal or the next release |
| Duplicate worlds on every backend (`%world_name%` lists 3) | Mirages | See `docs/mirage-dimensions.md` — intended |
| `distributeddimensions` channel does not appear in logs | Channel registration failed at boot (see `dropped-*` counters / `/ddproxy status`) | `/ddproxy reload`; restart proxy; check velocity console for the `channel ... NOT REGISTERED` line |

## 12. What this guide deliberately does not cover

- Docker/Kubernetes/Compose layouts — bring your own; nothing here requires them.
- HA/multi-proxy setups — Velocity supports them; this plugin is untested in that shape.
- BungeeCord networks — different forwarding model, unsupported.
- Bedrock (Geyser/Floodgate) players — untested; claims welcome after real testing.
- Offline-mode networks (`online-mode=false` on the proxy) — out of scope for production.
- Upgrades/migrations between plugin versions — only `config-version` migrations exist;
  the plugin is pre-release, so treat every upgrade as a reinstall on staging first.

When in doubt: the logs on the proxy and each backend name the exact failing subsystem.
Read them before restarting anything.
